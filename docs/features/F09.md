# F09 — Voice and USSD Transactions

Date: 2026-10-15  
Status: **RUN_PASS for the expense-only USSD application and authenticated competition simulator; BLOCKED_EXTERNAL for a live Pakistan gateway; payments and income remain NOT_STARTED**.

## Scope and acceptance

An active farmer with a Fasal Guard phone number and separately configured PIN can use a signed USSD session to select an owned farm and active crop season, choose an expense category, enter whole PKR, review the exact transaction, and explicitly confirm it. Confirmation creates one append-only expense and one confirmation event. Cancel, expiration, invalid input, wrong PIN, replay conflict, lost permission, or missing confirmation creates no expense.

The slice does not initiate payments, transfer money, create income/harvest transactions, recover PINs, or authorize transactions from voice input.

For demonstrations before a carrier contract is available, an authenticated browser simulator runs the same state machine against the same farms, crop seasons and ledger. It is persistently labelled `SIMULATION`, requires acknowledgement, and states that no operator, short code or money transfer is involved. A confirmed demo expense is a real ledger write.

## Data model and guarantees

Migration `1755000043000` creates:

- `ussd_credentials`: Argon2id PIN hash, global failure count and timed lock.
- `ussd_sessions`: gateway/session uniqueness, phone HMAC, authoritative state/context, bounded steps, expiration and terminal response.
- `ussd_callback_receipts`: unique gateway event, canonical request hash and cached response. It stores no raw payload or PIN.
- `farm_ledger_entries`: integer minor units, PKR-only expense, unified User/Farmer/Farm/CropSeason foreign keys, unique source session and client reference.
- `farm_ledger_events`: one confirmation event per ledger entry.

Database triggers reject updates and deletes to ledger entries and events. Confirmation locks and revalidates the session, active farm and crop-season ownership, then writes the ledger/event and terminal receipt in one PostgreSQL transaction. Ten concurrent confirmation requests return one receipt and produce exactly one ledger row and event.

## API contracts and flow

- `POST /api/v1/ussd/pin/setup`: Farmer JWT plus current account password; creates or replaces a 4–6 digit nontrivial Argon2id PIN.
- `POST /api/v1/channels/ussd/callback`: transport endpoint authenticated by timestamped HMAC. It is disabled by default and the local contract adapter is rejected in production.
- `GET /api/v1/farm-ledger`: Farmer JWT; returns at most 100 caller-owned rows.
- `POST /api/v1/ussd/demo/callback`: Farmer JWT; accepts UUID event/session IDs and a maximum 32-character response. It derives the active farmer phone server-side and is disabled unless `USSD_DEMO_ENABLED=true`.
- Web BFF: `POST /api/ussd-demo/session`, `POST /api/ussd-demo/pin`, and `GET /api/farm-ledger`. HttpOnly session cookies stay server-side and mutation routes enforce same-origin requests.

Flow: signed callback → phone-bound session → PIN lock/verify → owned farm → owned active crop season → category → bounded whole-PKR amount → Pakistan-local current date → review → explicit confirmation → atomic ledger/event/receipt → owner-authenticated read.

The current signature covers canonical validated JSON fields for local application testing. A real adapter must follow its provider's raw-body signature, replay, key-rotation, source-network and response contract.

## Dialer-style demo (web and mobile)

Both front ends offer a keypad: dial `*3275#` and press Call to open the same simulated session. Any other code returns "Connection problem or invalid MMI code". This is still a simulation; the system phone dialer cannot reach this backend without an operator short code.

## Security, privacy and limitations

- The callback fails closed when disabled, unconfigured, stale, unsigned, or modified. Production rejects the test-only adapter.
- PIN setup requires an authenticated session and current password. PINs are never stored; failed attempts lock the credential globally.
- PostgreSQL stores a keyed phone digest, callback hash and minimal state. Callback bodies and PIN input are not retained.
- Money uses bounded integer paisa and a PKR database constraint. The feature records expenses; it does not move money or calculate credit.
- The existing identity schema lacks an explicit phone-verification timestamp. Live rollout must prove phone ownership before enabling USSD.
- Payload-conflict and phone/session-mismatch attempts are rejected and create durable metadata-only security events without retaining raw bodies, phone numbers or PINs.
- PIN credential version is bound when authentication succeeds and rechecked during confirmation; changing the PIN invalidates the pending session.
- Provider-facing failures currently use the global JSON error contract. A selected gateway may require bounded plain-text failure responses and provider-specific retry semantics.
- Live Pakistan USSD is `BLOCKED_EXTERNAL` on a short code, documented callback contract, credentials, commercial access and sandbox evidence.
- Browser network failure never queues a financial confirmation in the background. The UI retains the same event UUID and offers an explicit retry, so callback idempotency applies without silently submitting stale intent.
- The simulator is not evidence of GSM delivery, operator availability or feature-phone usability. Live Pakistan USSD remains blocked on a provider agreement, short code and private callback contract.

The demo design follows GSMA guidance to keep USSD interactions short and acknowledges timeout/confusion risks. The UI uses one labelled response field, live status updates and semantic forms. Urdu localization and a paired SMS receipt remain future work; bidirectional numbers and receipt IDs must stay isolated when Urdu is added.

## QA remediation (2026-10-16)

- Concurrent confirmations of one USSD session: callbacks queue on the session row lock. A caller that waits past `lock_timeout` (3 s) or loses a deadlock now retries up to 3 times in a fresh transaction, where it sees the finished session or stored receipt and returns the same idempotent result. If the session is still busy it answers a clean `409 USSD_SESSION_BUSY` (the gateway may retry the same callback) instead of HTTP 500. Covered by a Jest integration test that holds the session lock for 3.5 s while 6 confirms run. (QA F09 D3.)
- Production note (QA D6): append-only is enforced by triggers; the application database role must not be owner or superuser and must lack `TRUNCATE`.
