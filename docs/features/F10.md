# F10 — Multilingual Farmer Assistant

Date: 2026-10-15
Status: **IMPLEMENTED; TESTED_PASS against a disposable stack with a contract-stub provider; real-model validation BLOCKED; NOT complete and NOT production-ready.** Independent review has not happened.

## Scope and source repositories

Smallest vertical slice: an authenticated farmer asks a question in English, Urdu or Hindi and receives an answer that is accepted only if it cites approved knowledge articles retrieved for that question. Otherwise the assistant abstains. Suggested actions remain pending proposals.

- Active source: `fasalguard-ai`, branch `master`. Existing worktree changes were preserved.
- Architecture stayed in the existing NestJS API and PostgreSQL. The brief named FastAPI; that was reviewed with the owner and a duplicate service was not created.
- Reference: Khetscope (`banokabal/kissan-alert-solution`, SHA `6a5f143eab72eeac938f9d1dab9ce0cb084c530b`). Its README claims MIT but ships no LICENSE file, so it was **reference-only; no code was copied**. It is also not retrieval-augmented: context is client-supplied, outages produce fabricated weather and translations, and custom provider URLs are an SSRF risk. See `docs/audit/LICENSE_MATRIX.md`.

## Existing vs newly implemented

Existing and reused: Farmer-role conversation routes with farm/field ownership checks; server-derived owned context (crop, satellite, weather risk, scans, tasks, outbreaks) with exact coordinates excluded; the Qwen provider and fake provider; versioned `knowledge_articles` with `APPROVED` status; JWT/role guards; metrics.

New in this slice:

- Migration `1755000044000-assistant-grounding`: `assistant_messages.language`, `citations`, `grounding`, `idempotency_key`, a unique partial index for idempotent sends, and a GIN full-text index over approved articles (`'simple'` configuration: no stemming, usable for Urdu/Hindi script).
- Retrieval noise control (`retrieval-query.ts`): questions are tokenised, English/Urdu/Hindi stop words and tokens under 3 characters are dropped, and a row must contain at least 2 distinct meaningful terms when the question has 5 or more (1 otherwise). No meaningful terms means no sources and a fixed abstention. Off-topic questions such as "what is the capital of France" now retrieve nothing. Known limit: a 2-4 term off-topic question that contains one generic word present in an article (e.g. "weather") can still retrieve it; the citation check and the model are then the remaining guard. Specs: `test/retrieval-query.spec.ts`, `test/retrieval-abstention.integration-spec.ts` (`QA12_TEST_DATABASE_URL`, db `qa12_test`).
- `KnowledgeRetrievalService`: bounded OR-term search over `APPROVED` articles in the requested language only. Search terms are extracted as unicode letter/mark/digit tokens, so user text cannot inject tsquery syntax.
- Citation enforcement in `AssistantService.message`: no matching source means no model call and a fixed human-written abstention in the question language; an answer without citations, or with any citation that was not retrieved, is discarded and replaced with the abstention. Only server-known `{id,title,revision}` are persisted.
- Language: explicit request value, else the farmer's saved preference, else English.
- Idempotent send via `idempotencyKey`; a retry or concurrent duplicate returns the stored answer.
- Gemini provider (Google AI Studio): key in a header, one retry for 429/5xx only, a single deadline covering both attempts, strict JSON schema, shared parsing with Qwen.
- Config: `ASSISTANT_PROVIDER` accepts `gemini`; production rejects the fake assistant and requires the selected provider's key.
- `POST /assistant/conversations` now returns the created conversation (it returned an empty message list, so clients had no id).
- Web: BFF routes `app/api/assistant/conversations[/id[/messages]]`, chat panel with farm/language selection, history, sources, "no approved guidance" state, error with Retry that reuses the idempotency key, session-ended state, `dir="auto"` for RTL. A voice transcript only fills the question box; the farmer presses Ask.

## Data flow and endpoints

Browser → Next BFF (same-origin, HttpOnly cookie, origin check on mutations, zod validation) → `POST /api/v1/assistant/conversations`, `GET /conversations[/:id]`, `POST /conversations/:id/messages` `{message ≤4000, language en|ur|hi (optional), idempotencyKey uuid (optional)}` → ownership check → language resolution → full-text retrieval of approved articles → (only if sources exist) provider call → citation check → one transaction writing the user message and the assistant message → response `{id, content, language, grounding GROUNDED|ABSTAINED, citations[{id,title,revision}], proposals[], requiresExplicitConfirmation}`.

Cross-lingual retrieval is not attempted: a question is answered only from approved articles in its own language. A language with no approved articles abstains.

### Stability note

Back-to-back E2E runs sometimes failed (e.g. farmer B receiving 401, the page redirecting to login) while runs after an idle gap passed. The most likely cause is the global API limit of 120 requests per minute per IP: a run uses much of it, and `proxy.ts` treats any non-OK `/auth/me` response (including a rate-limit response) as signed-out, redirecting to login and clearing the cookies. This was not proven by a captured 429, so treat it as a hypothesis. Run the script at least a minute after the previous run. The proxy behaviour is an existing auth defect outside F10 and is worth a separate fix.

## Voice: speech-to-text and text-to-speech

Added after the first F10 pass, using an AssemblyAI key supplied by the owner.

**Speech-to-text (AssemblyAI) — working and tested.** `AssemblyAiSpeechProvider` reads the farmer's private recording from our signed URL, uploads the bytes to AssemblyAI, requests a transcript with the selected language code (`en`, `ur`, `hi`), polls under one deadline, and returns the text plus a confidence value. It is selected with `SPEECH_STT_PROVIDER=assemblyai` and `ASSEMBLYAI_API_KEY`. Provider error bodies are never echoed, and the key is only in a header. The capabilities endpoint now combines the speech-to-text provider and the text-to-speech provider (for example `ASSEMBLYAI+FAKE`).

**Text-to-speech — no server provider available.** AssemblyAI does not synthesize speech, and no Azure or Qwen key exists, so server playback (`Play transcript`) stays disabled. Instead each assistant answer has a **Listen** button that uses the browser's own `speechSynthesis` voice for `en-US`, `ur-PK` or `hi-IN`; the text never leaves the device. If the device has no voice for the language, the farmer is told so plainly.

**Defect found and fixed while testing.** Chrome and Android record WebM/Opus and Safari records MP4. The media policy only validates WAV (16 kHz, mono, 16-bit) and Ogg/Opus, so a WebM upload was rejected at `/api/uploads/complete` with `UNSUPPORTED_AUDIO_CODEC` and a farmer on Chrome could never transcribe anything. The recorder now converts the recording to 16 kHz mono WAV in the browser (Web Audio decode and offline resample, `features/conversations/wav-encoder.ts`) before upload, and the AssemblyAI adapter advertises only the formats the server can validate. Server-side validation was not loosened.

## Security and privacy

- Owner isolation on every route; farm/field selection re-checked server-side; client-supplied context is ignored.
- Untrusted text (question, retrieved articles) is passed as JSON data with a system prompt that forbids following it; model output is parsed against a strict schema; actions must be on the server allowlist and are never executed.
- Model text is shown only if every cited id was retrieved; otherwise it is dropped, so a forged citation cannot produce an uncited claim.
- Provider key travels in a header, is never logged or placed in a URL, and provider error bodies are not echoed to clients. Questions, prompts and coordinates are not logged.
- Production configuration refuses the fake assistant.
- Conversation history is retained indefinitely; a retention and deletion policy is still required.

## Limitations and blockers

1. A valid provider key (Google AI Studio `AIza…` key, or a Qwen/Claude key with an adapter) is required for any real-model evidence.
2. A legally usable, expert-reviewed corpus in English, Urdu and Hindi is required before farmers can receive real answers.
3. Retrieval is lexical and same-language only.
4. Independent review, including prompt-injection testing against a real model, is outstanding.

## QA remediation (2026-10-16)

- Input hardening: assistant `message` (and conversation `title`, speech `text`) reject NUL and other C0/DEL control characters with 400 (tab, LF and CR remain allowed); whitespace-only messages are rejected with 400. Previously a NUL returned HTTP 500 from PostgreSQL. (QA F10 D4, D8.)
- Provider outage mapping: Qwen and Gemini timeouts, network failures and non-2xx answers all become `503` with the stable body code `ASSISTANT_PROVIDER_UNAVAILABLE` (Qwen previously leaked a 500 `TimeoutError`). Nothing is persisted. (QA F10 D5.)

## Extractive provider (2026-10-23)

`ASSISTANT_PROVIDER=extractive` answers with a short verbatim excerpt (about 520 characters, sentence-trimmed, plus the article's own closing expert-consultation line) from the top 1-2 retrieved approved articles, cites exactly those ids and revisions, and needs no model or key. The lead-in names the article title so the DEMO label stays visible. With no retrieved source the existing fixed abstention applies. Responses are tagged provider `EXTRACTIVE`, model `extractive-quote`. It is quote-only: it never paraphrases or adds advice. Urdu/Hindi lead-in wording is UNVERIFIED by a native reviewer.
