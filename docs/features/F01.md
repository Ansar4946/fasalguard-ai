## Existing behavior and gaps

Existing flow: browser private upload -> Next BFF -> NestJS crop-scan creation/attachment -> BullMQ -> quality/inference provider -> PostgreSQL predictions/diagnosis -> browser polling/results. FastAPI currently supplies `/v1/vision/quality`, `/v1/vision/predict` and `/v1/vision/models`; it does not implement scan ownership/persistence or Celery.

Existing user/farmer/farm/field/crop-cycle records and scan/prediction tables must be reused. `crop_scans` currently links owner and optional field; the worker chooses the latest active crop cycle at execution time. That can change between submission and processing and does not preserve the requested CropSeason identity. Plan: bind a crop season when the scan is submitted, then retain it in inference provenance.

Current gaps: no checked-in ONNX weights (models directory contains README only); provider configuration and actual access not exercised; missing crop-aware self-hosted model routing; incomplete distinction between bad photos and provider outages; no F01 FastAPI authorization/persistence; no Celery transport/outbox; prediction writes need atomicity and duplicate-delivery protection; no full cross-owner UI-to-data evidence.

Security prerequisite: `services/api/src/domain/auth/auth.service.ts:login()` selects by identifier and issues tokens without password/OTP verification. This is confirmed source behavior, not a hypothetical concern. F01 cannot claim private farmer access until credential verification is restored and tested. Do not silently change the login UX: address its contract explicitly as a small prerequisite work package.

Python inference endpoints currently have no authentication dependency. Protect sensitive vision routes via a verified internal-service credential or equivalent authenticated gateway boundary; network placement alone is insufficient.

## B. Smallest working vertical slice and identity mapping

Use the existing FastAPI service rather than adding a third backend framework. Proposed Python package `services/geospatial-ai/app/f01/` contains schemas, auth, repository, media validation, provider adapter, service/router, Celery tasks and outbox dispatcher. Preserve the existing stress-analysis/market endpoints.

Unified identity mapping: User -> `users.id`; Farmer -> `farmer_profiles.id` (unique user_id); Farm -> `farms.id` (farmer_id); Field -> `fields.id` (farm_id); CropSeason -> existing `crop_cycles.id` (field_id/crop_id/status/dates). Expose cropSeasonId as an API name for this existing record. Do not create parallel users/farmers/crop_seasons tables.

FastAPI validates current access JWT algorithm, issuer, audience, expiry, type=access, sub and sid; then joins auth_sessions/users to enforce active, unrevoked sessions. Resolve roles from the database, not a client header. Ownership queries join field -> farm -> farmer profile -> user, and check deleted state and season-to-field membership. Workers revalidate scan/season/media ownership and eligibility.

Schema authority remains the existing versioned TypeORM migration chain during transition. Add an additive migration (next unused number determined immediately before implementation), not a second migration history over the same tables. Add nullable crop_season_id FK to existing crop_cycles and backfill only unambiguous cases; new field-bound scans require a valid season. Add attempt/version metadata, unique per-attempt result constraints and durable outbox/audit records only where absent. Keep legacy scan/diagnosis table names and semantics needed by expert review, follow-up, risk, dashboard and offline sync. Inspect their triggers/consumers before changing statuses.

Queue submit transaction: lock scan -> validate state/evidence/season -> snapshot provider policy -> insert attempt and outbox event -> commit. Dispatcher publishes only attempt IDs to a dedicated Celery queue in Redis and marks dispatch durably. Task claims attempt with a database lease; duplicate delivery is harmless. Persist model prediction, alternatives, diagnosis, audit and terminal state atomically. On retry create a new attempt and preserve earlier provenance. Recover expired leases/stuck jobs; cap retries to 3 with backoff for transient provider errors only.

During rollout, only one backend may write/queue F01 for a scan. Gate the Next F01 BFF routes to the Python URL; disable/drain legacy crop-scan BullMQ producer/consumer before enabling the new writer. Retain old routes/read behavior for existing records and downstream integrations. Do not replay existing jobs blindly.

## Data flow and API contracts

Preserve external web routes `/api/crop-scans`, `/api/crop-scans/{id}/images`, `/api/crop-scans/{id}/analyse`, `/api/crop-scans/{id}`, existing uploads and owner-only temporary media URLs. Add cropSeasonId and model provenance additively; do not remove current response properties. Backend FastAPI routes use `/api/v1/crop-scans` for compatibility.

| Route | Contract proposed |
|---|---|
| POST /api/v1/crop-scans | owned fieldId + cropSeasonId; 201 CropScan |
| POST /api/v1/crop-scans/{id}/images | mediaId + existing category; validate ready/private/owner/state/count; 200 CropScan |
| POST /api/v1/crop-scans/{id}/analyse | 202, scan ID/status/attempt ID; idempotency key and atomic transition |
| GET /api/v1/crop-scans/{id} | owner-only compatible result plus attempt/model/source provenance; no raw private provider response |
| GET /api/v1/crop-scans?fieldId=...&limit=...&cursor=... | owner-checked bounded paginated history; keep old caller shape via BFF adapter if needed |
| POST /api/v1/crop-scans/{id}/retry | retryable failures only; 202 or 409 |
| GET /api/v1/crop-scans/capabilities | configured provider/model/crops/limits; no secrets; register before dynamic ID route |
| GET /api/media/{id}/access-url | reuse existing authenticated short-lived private access contract |

Common error shape: `{error:{code,message,requestId}}`. Distinguish invalid input (400/413/422), unauthenticated (401), forbidden role (403), concealed foreign resource (404), state conflict (409), unavailable dependency (503). Stable codes include MODEL_NOT_CONFIGURED, CROP_NOT_SUPPORTED, PROVIDER_TIMEOUT, PROVIDER_UNAVAILABLE and INVALID_PROVIDER_RESPONSE. Define terminal outage states additively after checking existing consumers; do not overload NEEDS_FOLLOW_UP with operational failures.

Flow: Next session BFF -> FastAPI authorized scan command -> same PostgreSQL identities/media records -> durable outbox -> Celery -> private object bytes -> reviewed provider -> validated finite scores and classes -> atomic persistence -> Next polling/results. Existing symptoms/severity/follow-up routes keep operating against the same scan IDs.

## Security, privacy, limitations and blockers

Photos remain private, EXIF stripped server-side, temporary media URLs issued after ownership checks, no arbitrary provider URLs or object keys accepted from clients. Retention/deletion and provider consent apply to photos and raw responses; keep minimal auditable model metadata. Rate limits and bounded request/worker execution prevent uncontrolled image/resource use. Separate screening model score from calibrated disease probability and future risk; no automatic chemical treatment from a classifier.

Preserve unrelated features and staged work. Production cannot be claimed while these remain.

## Independent Codex plan review — corrections incorporated

A separate Codex agent reviewed this plan against current source. This is a plan review only; independent implementation review remains mandatory before completion.

- Preserve image-retake workflow: NEEDS_FOLLOW_UP due to image quality permits owner-authorized evidence amendment and a new attempt. Transient provider failures use retry without changing evidence. Do not restrict all reanalysis to operational failures. Never modify inputs of an active/completed attempt; keep their image/season snapshots immutable.
- Snapshot season eligibility at submission. At processing recheck ownership, deletion/privacy policy and the scan's bound season relationship, but do not reject an already valid queued scan solely because its season was harvested while waiting. Later active seasons cannot replace the saved season.
- Define route ownership explicitly: Python owns create/attach/analyse/retry and attempt persistence after cutover; legacy symptoms/observations, severity, expert-review and follow-up commands continue to use the same records. Those consumers must read the saved season when present and fall back only for legacy records.
- Fence processing in the database with a writer generation/lease checked on claim AND result commit. Disable new legacy producers, drain or safely cancel their queued/running jobs, and wait for active claims before enabling the Python generation. A BFF flag alone cannot prevent stale BullMQ writes. Test stale worker commit, duplicate Celery delivery and cutover rollback.
- Migration rollback must stop/drain the new worker and disable Python routing before reversing additive schema. Retain new evidence/attempt history through deployment rollback; do not drop populated columns/tables as an automatic operational rollback.
- Preserve `CropScanService.listRecentForField()` as the existing diagnosed-evidence picker contract. Add paginated all-state history separately; test that incident follow-up pickers never receive queued/failed scans as usable diagnosis evidence.
- Credential prerequisite covers LoginDto, sign-in UI, BFF contract and password/OTP verification, including a test that identifiers alone cannot issue tokens. Registration currently emails plaintext passwords; replace this with a one-time setup/verification flow and test that no password is emailed/logged. This is necessary to establish the privacy boundary, not an unrelated auth rewrite.
- Scope localStorage scan drafts to authenticated account IDs; clear private previews/drafts on logout and account switch. Test that a second farmer on the same device cannot inherit another farmer's scan or image preview.
- Initial execution budgets: each provider request 20s, <=3 images, one provider attempt per task invocation, Celery soft/hard limits 120s/150s, lease 180s with safe renewal, Redis visibility timeout >=300s. Recovery must fence expired task commits. Integration tests simulate timeout, worker termination and recovery; tune budgets using measured latency before deployment.
- Preserve existing risk-enqueue, AI-run telemetry and lifecycle-notification behavior through dedicated idempotent outbox effects keyed by scan/attempt/effect. Inference completion must commit independently of downstream notification outages. Test duplicate effects and retry failures without duplicate predictions or emails.

Review outcome: suitable to proceed with the corrected plan; no independent implementation review or working feature evidence exists yet.
