## Existing versus newly implemented

Existing reusable code included the authenticated assistant controller/service, unified user identity, private `media_assets`, assistant conversation tables, object-storage presign/complete/access flow, and farmer assistant route. Before F08, the microphone only toggled a label, answers and farm context were fixtures, `FakeSpeechProvider` returned a fabricated transcript and base64 text labelled as MP3, Hindi was absent, and no browser-to-speech API route existed.

New behavior:

- `FakeSpeechProvider` is unavailable and throws; production configuration rejects `SPEECH_PROVIDER=fake`.
- Azure Speech is an explicit credential-gated provider. Capabilities report no supported languages until configured.
- Browser recording requires permission and an explicit persisted consent grant. Clearing the checkbox persists revocation, and the UI changes state only after the API succeeds.
- Transcription accepts only an owned, completed `voice-note` audio asset after confirming active consent. Wrong-purpose and cross-owner assets fail authorization.
- Voice-processing consent is persisted under policy `2026-10-voice-v1`; both transcription and synthesis require the latest event to be an active grant for that version.
- Completed WAV/Ogg media is parsed server-side. WAV must be mono 16 kHz 16-bit PCM, Ogg must contain mono Opus, and either format must be no longer than 60 seconds.
- Urdu, Hindi, and English are explicit API languages. The transcript is editable and no diagnosis/action is fabricated.
- A private-manifest evaluator computes WER, CER, crop-term accuracy and latency from labelled, consented samples. It exits `BLOCKED_EXTERNAL` when prerequisites are absent.

## Contracts and data flow

`GET /api/v1/assistant/speech/capabilities` is farmer-authenticated and returns provider availability, verified configured languages, accepted MIME types, maximum recording duration and consent version.

`POST /api/v1/assistant/speech/consent` accepts `{granted, consentVersion}` and persists a versioned grant or revocation for the authenticated user.

`POST /api/v1/assistant/speech/transcribe` accepts `{mediaAssetId, language, consent:true, consentVersion}`. The service requires the latest consent event to be an active current grant, owner-checks the ready voice-note record, creates a short-lived private URL, calls the configured provider, and returns transcript plus provider/model provenance.

`POST /api/v1/assistant/speech/synthesize` accepts `{text, language, consentVersion}`. It requires previously recorded current consent and returns bounded base64 audio plus content type and provider/model provenance.

Browser flow: persisted consent grant → `MediaRecorder` → `/api/uploads/presign` → private object upload → `/api/uploads/complete` with server audio validation → authenticated Next BFF → core API → Azure Speech → editable transcript. Clearing consent persists revocation. Azure short-audio input is deliberately advertised only for `audio/ogg` and `audio/wav`; unsupported browser codecs disable recording honestly.

Database migration `1755000042000` extends the existing `consents.type` check constraint with `VOICE_PROCESSING`. No new database or duplicate backend was introduced.

## Security, privacy and scientific accuracy

- Audio requires browser permission and per-use affirmative consent. Consent is versioned and persisted.
- Media remains owner-scoped and private. The speech provider receives a short-lived signed URL; URLs, audio and transcripts must not be logged.
- API rate limits remain 10 transcription and 20 synthesis requests per minute per authenticated context.
- Provider calls have bounded timeouts and response sizes with stable 503 errors. Credentials stay server-side.
- No transcript, diagnosis, recommendation, translation or synthetic audio is fabricated when the real provider is unavailable.
- Real accuracy must be measured separately by language, script, noise, accent and crop vocabulary. WER/CER thresholds have not been approved, so production model quality is not claimed.

## Limitations and blockers

- No Azure Speech credentials are configured in the current environment.
- No legally usable, consented, labelled Urdu/Hindi/English clean/noisy corpus was supplied. Therefore real STT WER/CER, crop-term accuracy, latency and TTS listening quality could not be run.
- Chromium commonly records WebM, while the selected Azure short-audio REST contract is advertised only for WAV/Ogg. Unsupported clients receive a truthful typed-input fallback; broader browser recording needs a vetted transcode or Azure SDK/token design.
- The slice does not yet persist a transcript into an assistant conversation; the farmer reviews it in the editor first. Existing conversation APIs remain unchanged.
- A real microphone/device E2E and human TTS listening test remain blocked on the same credentials/corpus/device prerequisites.
- Independent review approved code correctness and security for the consent-gated application slice after the final corrections. `PRODUCTION_VERIFIED` still requires real-provider and device evidence.
