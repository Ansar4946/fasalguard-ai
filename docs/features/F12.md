# F12 — Notifications

Date: 2026-10-16
Status: **IMPLEMENTED; TESTED_PASS on a disposable stack (unit, PostgreSQL integration, real-browser E2E). Real push delivery to a phone and SMS are BLOCKED; mobile push registration is wired and logic-tested but unverified on a device. Not production-ready. Independent review has not happened.**

## Scope and source repositories

Smallest vertical slice, agreed with the owner: make the farmer's notifications real on web and mobile, add preferences and quiet hours, enforce them, and stop displaying invented alerts. SMS is recorded as blocked, not scaffolded.

- Active source: `fasalguard-ai`, branch `master`. Existing worktree changes were preserved.
- Architecture stayed in the existing NestJS API and PostgreSQL: the whole notification backend (tokens, notifications, deliveries, BullMQ queue, FCM provider) already lived there. The brief named FastAPI; a second service would have duplicated it.
- Reference: `kissan-alert-solution` has a real FCM v1 sender but ships no license file, so it was reference-only and nothing was copied; our own provider already follows that flow and additionally records one delivery row per message. Africa's Talking (SMS) is commercial and its Pakistan coverage is unconfirmed (`docs/audit/LICENSE_MATRIX.md`).

## Existing vs newly implemented

Existing and reused: `notifications`, `device_tokens`, `notification_preferences`, `notification_deliveries` tables; `createNotification` (deduplication key, consent gating, emergency-wording safety policy, BullMQ job with 4 attempts and exponential backoff); `FirebaseCloudMessagingProvider`; push-token register/delete; per-notification read; tasks; producers (farm brain).

Newly implemented:

- **Real web inbox.** `/alerts` previously rendered four hardcoded alerts ("High-risk cotton disease … Green Valley Farm", "Dr. Arshad responded…") and the header bell always said "2 unread". Both are replaced by data from the API: list, filters, mark read, mark all read, honest empty/error/unauthorized states, and delivery wording that never claims more than was recorded (`SENT` is shown as "Push sent (delivery not confirmed)").
- **Unread count and bulk read** endpoints; list supports `unreadOnly` and `limit` with strict parsing.
- **Preferences API and UI** (the DTO existed but no route did): per-category push on/off and quiet hours with time zone, with validation (both times or neither, start must differ from end, valid IANA zone).
- **Quiet hours are now enforced.** They were stored but ignored. A notification created inside the window is stored and shown immediately; its push is scheduled for the end of the window (delivery `scheduled_at` and a delayed queue job). `urgent: true` bypasses it; no producer sets that yet.
- **Consent notice:** the settings panel says why push is off when notification consent is not granted.
- **Mobile inbox** (`mobile/src/NotificationsPanel.tsx`, logic in `mobile/src/notifications.mjs`): list, unread label, mark read/all, refresh, push on/off per category, same error states; shown only with a stored authenticated session; HTTPS only.
- **Production now rejects `PUSH_PROVIDER=development`**, which reports unsent messages as `SENT`.
- **`RATE_LIMIT_PER_MINUTE`** (default 120, unchanged) makes the global per-IP API limit configurable.

## Data flow and endpoints

Browser or app → Next BFF (same-origin, HttpOnly cookie, origin check and zod validation on mutations) or direct HTTPS with a bearer token on mobile → Farmer-role endpoints:

- `GET /notifications?unreadOnly=true|false&limit=1..100` → own rows newest first, each with `delivery` (counts by status).
- `GET /notifications/unread-count`, `POST /notifications/read-all`, `PATCH /notifications/:id/read` (own rows only; others return 404).
- `GET /notifications/preferences` → `{consentGranted, categories[7]}` with defaults; `PUT /notifications/preferences/:category`.
- Existing: `POST /devices/push-token`, `DELETE /devices/push-token/:id`.

Creation path (unchanged except quiet hours): `createNotification` → safety policy → insert with deduplication → consent check → read the category preference → compute quiet-hours delay → insert one delivery row per active token (skipping categories with push off) → queue jobs with that delay → processor sends through the FCM provider and records `SENT`/`INVALID_TOKEN`/`FAILED`.

### Stability note

The first E2E attempts failed in the second half. The API limit is 120 requests per minute per IP, and one browser run issues more than that (the web proxy also treats a rate-limit response from `/auth/me` as "signed out" and redirects to login). With `RATE_LIMIT_PER_MINUTE=2000` on the test stack every check passed, which supports that explanation. The default stays 120. Two consequences worth a separate fix: farmers behind a shared carrier IP can hit it, and `proxy.ts` should not log a user out on a 429 or 5xx.

## Push registration and the Firebase test

**What the owner supplied:** only `VITE_FIREBASE_API_KEY` (a Firebase *web* API key). A read-only check against Google confirmed the key is valid. It identifies a Firebase project but **cannot send push messages**, and nothing in this repository reads it. Sending needs a service-account private key, and an Android phone needs that project's `google-services.json`; neither exists here and neither can be created from the web key. So **no real push was sent and no real FCM token was obtained.** This is BLOCKED, not passed.

**Mobile registration wiring (new):**

- `expo-notifications` (SDK-matched `~57.0.23`) added; plugin added to `mobile/app.json`; `mobile/app.config.js` applies `googleServicesFile` from `EXPO_GOOGLE_SERVICES_FILE` only when set, so builds without it still work.
- `mobile/src/push-registration.mjs`: `enablePush` (permission, device token, register, remember the server token id), `disablePush` (delete, forget; a 404 counts as already removed; other failures keep the id for retry), `refreshPushToken` (re-register on rotation, only if push is on). Outcomes are explicit: `REGISTERED`, `PERMISSION_DENIED`, `UNSUPPORTED_PLATFORM`, `TOKEN_UNAVAILABLE`, `SERVER_REJECTED`. A build without Firebase configuration reports `TOKEN_UNAVAILABLE` ("no push configuration (Firebase)") and registers nothing.
- `mobile/src/push.ts`: the only native code (permission prompt, Android channel `default`, device token, encrypted storage of the server token id, token-change listener, quiet foreground display).
- `NotificationsPanel`: an explicit "Turn on / Turn off push on this phone" control; registration never happens silently. Sign-out makes a best-effort removal of the token so the phone stops serving the signed-out farmer (if the phone is offline the server keeps the token until another farmer registers it, which rebinds it, or it goes stale after `PUSH_TOKEN_STALE_DAYS`).

**Server-side defects found and fixed while reviewing the push path:**

1. FCM `INVALID_ARGUMENT` was always treated as a bad token, which also covers a malformed message payload; one bad payload would have permanently deactivated healthy phones. It now invalidates a token only for `UNREGISTERED` or an `INVALID_ARGUMENT` that points at `message.token`.
2. The FCM message now targets the `default` Android channel that the app creates.

**To complete the real push test (owner action):** in the Firebase console for this project (1) Project settings, Service accounts, Generate new private key; base64-encode the JSON into `FIREBASE_SERVICE_ACCOUNT_BASE64` and set `PUSH_PROVIDER=firebase`; (2) register an Android app with package `pk.fasalguard.mobile` and download `google-services.json`; (3) build with `EXPO_GOOGLE_SERVICES_FILE=./google-services.json npx expo prebuild` / `expo run:android` on a phone; (4) sign in, press "Turn on push on this phone", create a notification (for example through the farm-brain producer or a test script), and confirm the delivery row becomes `SENT` and the phone shows it. Until then the claim is "wired, contract-tested, not proven".

## Security and privacy

- Owner isolation on every route; cross-owner reads and writes return 404 and bulk actions only touch the caller's rows.
- Inputs validated twice (BFF zod, API class-validator and explicit checks); query values are parsed strictly because the global transforming pipe would otherwise coerce `unreadOnly=maybe` to `true` (found and fixed during testing).
- Mutations require same-origin requests; tokens stay in HttpOnly cookies on web and in the secure session store on mobile; mobile refuses non-HTTPS servers.
- Push tokens are stored hashed for uniqueness and excluded from reads; the FCM provider only talks to Google's token endpoint over HTTPS with a timeout.
- Consent: no delivery rows without a granted `NOTIFICATIONS` consent; the UI explains it.
- The emergency-wording safety policy and deduplication are unchanged and still tested.
- A 401 clears the displayed list so one account's notifications are never left on screen for another.
- Production now refuses the development push provider.

## Environment and operations

`PUSH_PROVIDER` (`development` or `firebase`; **production requires `firebase`** with `FIREBASE_SERVICE_ACCOUNT_BASE64`), `PUSH_TOKEN_STALE_DAYS`, `RATE_LIMIT_PER_MINUTE` (new, default 120), and for mobile `EXPO_PUBLIC_CORE_API_URL` (HTTPS) plus `EXPO_GOOGLE_SERVICES_FILE` (path to the Firebase `google-services.json`, build time only). Redis and the queue worker (`PROCESS_ROLE=worker` or `all`) must run for pushes; the inbox itself needs only PostgreSQL. Details in `docs/ENVIRONMENT_VARIABLES.md`. Existing production configurations that leave `PUSH_PROVIDER` unset will now fail validation until it is set.

## QA remediation (2026-10-16)

- `GET /notifications?limit=` now rejects `0` and values above 100 with 400 instead of silently clamping; only whole numbers 1..100 are accepted. (QA F12 D9.)
- Design note (QA F12 D10, unchanged by decision): `POST /devices/push-token` rebinds an existing token hash to the caller on purpose. A token identifies one physical install; when a phone changes hands or another account signs in, the last registrant owns it and the previous owner's registration stops receiving pushes (their delete returns 404). FCM tokens are high-entropy and never returned by the API, so takeover requires already knowing the token. Documented in `NotificationService.registerToken` and covered by the rebinding integration test.
